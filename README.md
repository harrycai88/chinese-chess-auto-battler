# 实时中国象棋大乱斗

**自动对战 · 参数调校 · 策略沙箱**

> 红黑两军各由一套策略指挥，在放大的棋盘上自动厮杀。你不下棋——你调数值、换策略、看胜率，然后把别人的「大神策略」拖进来打一场。

## 1. 这是什么

一台**自动对战实验台**。三件事必须同时成立，缺一件就失去存在意义：

| 承诺         | 含义                                                                     | 不成立的样子                                 |
|:------------ |:------------------------------------------------------------------------ |:-------------------------------------------- |
| **自动对战** | 双方完全由策略驱动，规则闭环，一局能从开局打到基地告破，全程不需要人插手 | 要靠玩家微操才好看；某些兵种或局面必然僵持   |
| **好调平衡** | 所有影响胜负的量集中在一处，改完立刻能跑成批对局看结果，改动有据可查     | 调一个数值只能靠猜；改完说不清是变强还是变弱 |
| **好接策略** | 外部策略是一个文件夹，放进来就能参战；它只能表达意图，不能改规则         | 想试新打法必须改引擎；策略可以「作弊」       |

三者互相支撑：**规则足够干净**，策略才敢自由发挥；**策略足够多样**，数值才暴露得出来；**数值足够透明**，观战才有意义。

### 你会用它做什么

- **看一局**：选两套策略，开战。全程可暂停、变速，不需要操作任何一个棋子。
- **调平衡**：改一个数值，下一局立刻生效；成批跑对局，读胜率、时长与兵种指标。
- **接策略**：把一套打法写成一个文件、登记一行，就能和内置策略约战。
- **验规则**：用契约测试确认「改这个数没有破坏那条设计意图」。

### 它不是什么

- 不是可对弈的象棋游戏：没有玩家操棋，没有联机匹配。
- 不是通用战斗引擎：所有机制都为这一盘棋服务。
- 不是特效演示：画面服务战况可读性，不反过来影响判定。

## 2. 快速开始

```bash
pnpm install
pnpm dev
```

打开控制台，选红黑两套策略，开始观战。

批量调参：

```bash
pnpm run sim -- --matches <局数> --seed <种子> \
  --red <策略目录> --black <策略目录> --config <配置路径>
```

契约与回归：

```bash
pnpm test
```

生产构建：

```bash
pnpm build
```

构建产物是纯静态站点，可以直接托管；批量仿真与测试不进产物。

> 脚本名与参数以 `package.json` 为准；上面是最小可用集合，新增能力不应破坏这些命令。

### 2.1 v0.1 已落地

- 两套内置策略：`全军冲锋`（标尺）与 `防守反击`（局势判断、阵型、集火、残血回城、炮位轮转、加时决策）。
- 30 个单位、8 Hz 决策、基地 / 加时 / 复活 / 统计全链路；士的巡防、炮的短射程与基地炮塔的几何契约都在其中；无头仿真可跑完整局。
- Canvas 2D 战场、Web Audio 过程化音效、战前配置、观战 HUD、结算与移动端战报抽屉。
- 20 条测试，覆盖确定性、黄金对局、意图拒绝、兵种机制、加时与统计自洽。
- 已知差异：外部策略文件夹、Web Worker、回放分享链接尚未接入；见 `docs/architecture.md`。

## 3. 技术选型

| 层         | 选型                                   | 职责                                                      | 为什么是它                                                                                              |
|:---------- |:-------------------------------------- |:--------------------------------------------------------- |:------------------------------------------------------------------------------------------------------- |
| 观战控制台 | Vue 3（Composition API）+ Tailwind CSS | 参数热调、胜率统计、结构化日志、策略切换                  | 响应式状态天然贴合「参数一动，界面和数据立刻跟着变」；原子化样式让控制台保持工具感，而不是游戏皮肤感    |
| 战场渲染   | Canvas 2D                              | 大棋盘、木质/玉石质感棋子、浮动血条、受击反馈、残影与粒子 | 无额外运行时依赖；棋子精灵预渲染，30 单位实测 160+ fps。PixiJS 作为后续可选替换，不影响规则 |
| 音频合成   | Web Audio API                          | 碰撞、开火、爆炸、传送等全部音效                          | **纯代码过程化合成**：没有素材要下载、没有解码要等待，触发即响；音色是参数，不是文件                    |
| 规则内核   | 纯 TypeScript `BattleEngine`           | 物理、状态机、战术调度、胜负、统计                        | 零 DOM、零框架、零渲染依赖。同一份代码可以跑在浏览器、Web Worker 和 Node 里                             |

关键不是「用了什么」，而是**依赖方向只有一个**：控制台、渲染、音频都依赖引擎，引擎不依赖它们中的任何一个。

## 4. 设计原则

1. **规则里没有魔法数。** 所有影响胜负的量都来自数值源；代码只负责「怎么用」，不负责「用多少」。
2. **策略只能表达意图。** 去哪、打谁、要不要变形或放技能；能不能做到、做多快、造成多少伤害，由引擎裁决。
3. **引擎不知道浏览器存在。** 不 import Vue / Pixi / Web Audio，不碰 DOM，不读系统时钟，不播声音。
4. **表现永不参与判定。** 动画可以迟到、可以掉帧、可以整个关掉，对局结果必须一模一样。
5. **每一局都可复现。** 同一份数值、同一对策略、同一个种子，必须跑出同一场仗。
6. **调参与观感互不干扰。** 调平衡不需要懂渲染，调观感不需要碰数值；控制台是仪表盘，不是皮肤。

## 5. 架构与数据流

```text
   数值源 / 策略包
          │
          ▼
  ┌───────────────────────────┐
  │        BattleEngine       │   固定步长 · 确定性 · 零 DOM
  └─────────────┬─────────────┘
                │
        ┌───────┴────────┐
        ▼                ▼
    状态快照          事件流
  （连续，可插值）   （瞬时，可丢弃）
        │                │
        ├────────────────┼────────────────┐
        ▼                ▼                ▼
    战场渲染层        音频合成层        观战控制台
   插值 · 表现       合成 · 混音     参数 · 图表 · 日志
```

### 5.1 分层契约

| 层     | 可以知道什么                       | 绝对不可以做什么                                   |
|:------ |:---------------------------------- |:-------------------------------------------------- |
| 引擎   | 数值源、策略返回的意图、自己的状态 | 引用渲染对象、播放音频、读写 DOM、使用未播种的随机 |
| 渲染   | 引擎发布的状态与事件               | 修改任何单位、血量、位置或胜负                     |
| 音频   | 引擎发布的语义事件                 | 影响战局节奏，或等待画面                           |
| 控制台 | 数值源、会话状态、统计与日志       | 绕过校验直接改引擎内部状态                         |

**唯一的反向通路**是「控制台 → 引擎会话」的显式操作：开始、暂停、变速、重开、切策略、改数值。这些操作走引擎公开的会话接口，不允许直接改单位或战局字段。

### 5.2 状态与事件

引擎每一步发布两类数据，用途严格分开：

| 数据         | 特征                                                                                   | 消费方式                               | 能否丢弃                                   |
|:------------ |:-------------------------------------------------------------------------------------- |:-------------------------------------- |:------------------------------------------ |
| **状态快照** | 连续量：位置、血量、形态、计时器、基地、阶段                                           | 渲染层在相邻两份之间插值；控制台读数值 | 可以丢中间帧，不能丢最终态                 |
| **事件**     | 瞬时事实：开火、命中、爆炸、展开、跃击、传送、死亡、复活、加时开始、基地告破、对局结束 | 渲染层放特效，音频层发声，日志层记录   | 可以合并、延迟、静音；不能改变已发生的结算 |

分开的理由很实际：插值需要连续量，音效需要瞬时触发。混在一起，表现层就会被迫理解规则，最终反过来影响规则。

### 5.3 一次决策的生命周期

1. 引擎按固定步长推进物理，与渲染帧率、浏览器是否在后台无关。
2. 到达决策点时，为**每个阵营各生成一份只读快照**——只包含该阵营视角的战场信息与公开数值，不含对方的策略状态。
3. 策略的三层管道把快照变成一组白名单意图。
4. 校验器逐条核对：归属、存活、距离窗口、星位相邻、目标占用、形态限制。合法意图写入单位，非法意图被拒绝。
5. 物理步执行这些意图，产生位移、伤害、击退、复活、基地流血与胜负变化。
6. 状态与事件发布给表现层。渲染可以晚一帧，音频可以丢一个音符，引擎不会等它们。

> 被拒绝的意图**不静默吞掉**：计数、记录原因、在控制台可见。策略作者最需要的是「为什么我这一手没生效」。

### 5.4 运行形态

| 形态        | 引擎在哪   | 用途                                           |
|:----------- |:---------- |:---------------------------------------------- |
| 浏览器观战  | 主线程固定步长（v0.1） | 30 单位 / 8 Hz 决策实测 160+ fps；引擎与渲染解耦。Web Worker 作为后续替换，接口不变 |
| Node 批量   | 进程内     | 无渲染、无音频，高速跑完成批对局并输出统计     |
| 单测 / 契约 | 进程内     | 直接驱动引擎，逐条验证规则不变量               |

三种形态共享同一份引擎构建产物、同一套配置加载与策略加载逻辑。**不存在「浏览器版逻辑」和「跑批版逻辑」两份代码。**

引擎对外只有五个入口：创建对局、推进、取状态、取事件、取结算统计。没有第六条路。

创建一局需要：配置、双方策略、种子、局时（可选）。表现层是否订阅事件与引擎无关——引擎不为渲染开关负责。

### 5.5 确定性

- 模拟只按固定步长推进，不依赖真实经过的时间。
- 随机数来自可播种的伪随机源；引擎内不出现系统随机与当前时间。
- 遍历顺序固定（按 id、按数组下标），不依赖对象键顺序做规则判断。
- 暂停、倍速、切标签页、关掉特效、静音，都不改变一局的结果。
- 同一运行时内逐帧可复现；浏览器与 Node 之间以**统计口径**对齐（胜率、时长、兵种指标），不承诺浮点位级一致。
- 策略超时会破坏可复现性，因此它被当作**显式失败**处理：记录、告警、该次决策按空意图继续，绝不静默重试。

## 6. 规则内核

### 6.1 战场

- 标准中国象棋棋盘，红方在下、黑方在上，双方镜像布阵。
- 开局按标准中国象棋阵型摆放，九宫中心由基地占据，替代帅 / 将。
- 逻辑坐标原点在棋盘左上角，x 向右、y 向下，以「格」为单位；渲染层负责像素换算、缩放与居中，引擎不知道像素。
- 九宫是双方基地的所在地，基地固定在九宫中心。
- 河界是双方半场的分界；象只能在己方半场活动。
- 每方半场的星位，就是象在象棋里能到达的那七个落点；只有相差一个「田」字的星位互为邻居；两只象不能落在同一星位。
- 常规军的出生点设有**不可被攻击的底座**，它同时是回血区与复活点；底座在棋盘上用「虚线圈 + 复活符」标出，单位阵亡时圈内直接显示复活倒计时；精英没有底座。
- 士的防区是**以己方基地为圆心**的一个圆：它可以在圈内自由走位、追击，但压不出圈；且它不允许站桩，没有指令时也会沿防区前沿来回巡走。
- **棋子不按象棋走法移动**：除象的星位传送与士的防区限制外，其余单位在棋盘上自由移动、自由寻路。

### 6.2 棋子

| 棋子            | 行为                                                         | 状态机                                 | 约束与弱点                                                   |
|:--------------- |:------------------------------------------------------------ |:-------------------------------------- |:------------------------------------------------------------ |
| 帅 / 将（基地） | 不可移动的火力点与胜负核心，炮塔自动索敌，也可被策略指定集火 | 静止                                   | 不能回血；被摧毁即战败                                       |
| 车              | 高速近战主力，劈砍会波及身边的敌人                           | 无技能状态                             | 依赖机动与阵型，被集火时同样会死                             |
| 兵              | 廉价前排，攻击附带击退与短暂硬直，能打断敌方节奏             | 无技能状态                             | 单体输出低，怕远程消耗                                       |
| 马              | 近战偏弱，靠跃击切入；腾空期间不可被选中，落地造成范围震击   | `WINDUP → DASH`                        | 起跳有距离窗口，贴脸与超远都无法起跳；落地后有一段真空期     |
| 炮              | 移动与架起两种形态；架起后才能发射高爆弹（不需要炮架）       | `MOBILE → DEPLOYING → SIEGE → PACKING` | 射程只够压到对面半场；能打到基地的站位一定在基地炮塔射程内；展开与收起各要一小段时间，期间更脆 |
| 士              | 基地护卫，在防区里持续巡走，扇形霰弹，距离越远伤害越低       | 无技能状态                             | 被引擎刚性限制在基地防区内，无法追击到远处；不能站桩；阵亡后归队极慢 |
| 象              | 不能行走，只能在己方星位之间按「田」字传送；落地震晕周围敌人 | `IDLE → WINDUP`                        | 前摇期间不能攻击且更容易被集火；射程短；靠自身缓慢自愈       |

### 6.3 一个物理步的顺序

顺序不是实现细节，而是规则的一部分：

1. 推进时钟，检查局时是否到点、是否该进入加时。
2. 若到达决策点：为双方各建快照 → 跑策略 → 校验意图 → 写入单位。未获得意图的单位**不主动移动**，但防御性自动攻击仍然生效。
3. 推进各类计时器：攻击与技能冷却、硬直、减速、表现计时递减；脱战计时累加。
4. 按意图与当前状态计算每个单位的期望速度（硬直、传送前摇、架起形态都会把它压成零）。
5. 执行兵种机制：索敌、开火、架起/收起、跃击、传送、被贴脸逃跑。
6. 积分位移：期望速度经加速度逼近，接近目标点时减速，叠加击退冲量，边界 clamp；交战中移动降速；士额外被 clamp 回防区。
7. 单位分离：按质量把重叠单位推开，基地不被推动。
8. 推进弹体：直击、爆炸、距离衰减、击退、减速。
9. 回血与复活：底座回血、精英自愈、复活读条。
10. 加时流血：双方基地等量扣血，**绕过伤害管线**。
11. 清理过期的事件与特效。
12. 判定胜负：基地是否存活。

其中两条最容易写错：

- **攻击冷却必须在位移之前更新**，否则「交战中减速」会晚一帧生效，全速走砍又回来了。
- **流血不能走伤害管线**，否则会吃攻城倍率、被计入输出统计、并把脱战计时重置成「正在交战」。

### 6.4 索敌与伤害

**索敌**遵循「显式优先、自动兜底」：

1. 策略指定的目标若存活、属于敌方、未被不可选中、且距离在「射程 + 目标半径」内，就用它。
2. 否则在同样条件内选最近的敌人。
3. 炮额外有最小距离：目标落在盲区内时锁不到，即使理论射程够。

距离判定统一用「中心距 ≤ 射程 + 目标半径」。这条约定让大体型目标更容易被够到，也意味着射程关系必须按最坏情况核算——**几何契约**就是为此存在的。

**伤害管线**：

```text
基础伤害
  → 情境倍率（对基地的攻城倍率 / 架起中的炮 / 传送前摇中的象）
  → 扣血
  → 重置攻击者与受击者的脱战计时
  → 记录来源与攻城统计
  → 死亡处理
```

- 攻城倍率只作用于「非基地单位打基地」，不影响单位之间与炮塔伤害。
- 击退是冲量除以质量，不取消当前意图，但会改变实际位置。
- 硬直阻止移动与攻击；减速只影响移动速度。
- 弹体只检测敌方单位：不误伤友军，也不做地形与友军碰撞；爆炸按距离衰减。
- 死亡会清空意图、重置形态；基地死亡直接结束对局。

### 6.5 移动

- 期望速度 → 加速度逼近 → 接近目标点按剩余距离减速 → 叠加击退 → 边界 clamp → 单位分离。
- **交战中移动降速**：只要攻击冷却未归零，就视为正在交战，移动速度按配置比例下降；停火且冷却归零后立刻恢复。
- 士的位置每步被刚性限制在基地防区内；象没有行走速度，位移只来自传送。
- 单位之间是软碰撞：重叠会被按质量推开，但不会硬性阻挡移动。
- 朝向优先级：移动方向 > 集火目标 > 攻击方向。朝向只影响表现与炮塔指向，不参与伤害计算。

### 6.6 回血与复活

| 类别                        | 回血                           | 阵亡后                                   |
|:--------------------------- |:------------------------------ |:---------------------------------------- |
| 常规军（车 / 马 / 炮 / 兵） | 回到自己的底座圈内且脱战足够久 | 读条复活，满血回到出生点；炮回到移动形态 |
| 精英（士 / 象）             | 脱战后按自身速率自愈，位置不限 | 读条极长（士 45s / 象 60s），常规时间里多数时候等于一次性；加时按倍率缩短 |
| 基地                        | 不可回血                       | 不可复活，被毁即战败                     |

复活会清空击退、硬直、减速与形态，但不会白送技能冷却——刚复活的马和象仍然要等自己的技能转好。

### 6.7 局时与加时

局时可以被设为不限时：此时不进入加时，直到一方基地被毁。

局时归零**不判平、也不停手**，而是进入加时——一个双方都在倒计时的决战：

1. **复活大幅加速**：所有单位的复活读条乘以加时倍率（包括士、象的长读条）；已经在读条中的单位按新节奏折算剩余时间，不会被瞬间跳过，也不会永远读不完，也不会白送复活。
2. **基地被毁才结束**：军队暂时全灭不算输——加时里补员很快，短暂无人可上是正常现象。
3. **同帧归零有确定性裁决**：先比流血前的基地血量，再比残存兵力评分，最后用战局种子裁决。仍然摧毁其中一座，不产生平局。
4. **安全上限只是兜底**：正常情况下流血会先结束对局；真走到上限，也仍然摧毁较弱的一方，而不是宣布平局。

这条规则的设计意图很明确：**常规时间打出的攻城伤害，就是加时的起跑线。** 带着更多基地血量进加时的一方，只要守住就赢；落后的一方必须在流血耗尽前把差距打回来。

### 6.8 胜负与结算

- 结果只有红胜、黑胜两种；结束原因区分为「基地被常规攻击摧毁」「基地被加时流血摧毁」「安全上限裁决」。
- 结算输出：耗时、结束阶段、双方基地剩余、双方兵力、逐兵种统计、双方策略标识、种子与配置指纹。
- 统计必须能直接喂给控制台与批量仿真，不允许「界面上一套算法、跑批里另一套」。

统计口径统一定义，避免同一个指标在两个地方算出两个数：

| 指标       | 定义                                            |
|:---------- |:----------------------------------------------- |
| 存活率     | 对局结束时该兵种存活数 / 初始数量               |
| 输出占比   | 该兵种造成的总伤害 / 同阵营所有单位造成的总伤害 |
| 攻城伤害   | 该兵种对基地造成、已计入攻城倍率的伤害          |
| 复活次数   | 该兵种成功返场的次数                            |
| 技能命中率 | 跃击命中次数 / 跃击释放次数（仅马）             |
| 架设阵亡比 | 在展开或架起状态阵亡的次数 / 该兵种阵亡总次数   |
| 非法意图率 | 被拒绝的意图数 / 提交的意图数                   |

## 7. 数值模型

### 7.1 单一数值源

一份结构化配置，按域分段：

| 域             | 管什么                                                                                                          |
|:-------------- |:--------------------------------------------------------------------------------------------------------------- |
| `global`       | 棋盘尺度、局时与加时、物理（加速度 / 刹车 / 阻尼 / 分离）、战术决策频率、攻城倍率、交战减速、评分权重、表现上限 |
| `base`         | 基地血量、半径、炮塔射程 / 伤害 / 射速 / 弹速                                                                   |
| `spawner`      | 底座半径、回血速率                                                                                              |
| `units.<type>` | 半径、质量、血量、移速、攻击距离 / 伤害 / 冷却、技能参数、脱战延迟、复活时间、自愈速率                          |

规则与约定：

- 代码只能通过带类型的配置访问器读取数值；**规则分支里不允许出现影响平衡的字面量**。
- CI 增加一条静态检查：规则包内不出现魔法数字（结构性常量如 `0`、`1`、`-1` 走白名单）。
- 新增字段必须给默认值，老配置不能因为缺字段而崩。
- 字段命名要回答「这个数在管什么」，而不是「这个数属于哪个变量」。

### 7.2 schema 校验

- 类型、范围、枚举、必填项；越界直接拒绝。
- 错误信息必须包含字段路径（例如 `units.cannon.min_range`）、当前值、期望范围。
- 配置带版本号；不兼容的旧版本给出明确的升级说明，而不是猜。
- 校验失败**保留上一份可用配置**，控制台显示差异与错误原因，绝不用半份坏配置开局。

### 7.3 热更新语义

| 改动                                       | 生效方式                                       |
|:------------------------------------------ |:---------------------------------------------- |
| 普通数值（血量、伤害、速度、冷却、倍率）   | 下一个物理步生效                               |
| 正在进行的计时器（复活、前摇、架设、收起） | 按新旧总时长比例缩放，避免瞬间完成或永远读不完 |
| 棋盘尺度、单位编成、星位拓扑               | 需要重开一局，界面明确提示                     |

改坏了可以一键回滚到上一个通过校验的版本。

### 7.4 预设与对比

- 三类别名：基线、候选、个人实验；随时切换，互不污染。
- 同一组种子对跑两套配置，输出逐项差异。
- 差异要能解释：哪个兵种、哪个阶段、哪项指标变了，而不是只给一个总胜率。

### 7.5 契约校验

数值改动最容易犯的错，是修好一个兵种、顺手毁掉一条设计意图。用不变量把它钉住：

| 契约     | 守住什么                                                         |
|:-------- |:---------------------------------------------------------------- |
| 单挑契约 | 某些兵种在特定条件下必须赢、某些必须输，防止「一个棋子打穿全场」 |
| 几何契约 | 射程关系必须保证不存在「我打得到你、你打不到我」的绝对安全站位；炮的射程上限由基地炮塔决定 |
| 经济契约 | 阵亡的代价必须高于回城治疗，杜绝「送死等复活」成为理性解         |
| 节奏契约 | 交战中的移动必须被惩罚，杜绝全速走砍                             |
| 加时契约 | 流血必然先于安全上限结束战局，规则自洽、不产生平局               |

契约测试失败时，输出必须是「哪条不变量、当前值、边界、可能受影响的兵种」，而不是一句 `expected true to be false`。

单挑契约需要一个**无基地、无战术、无复活**的单挑模式来跑：只让两个单位在指定初始距离下自动交战。它是测试夹具，不是第二种玩法。

### 7.6 调参账本

每次改动记录四件事：动机、旧值到新值、预期效果、实测结论（保留还是回滚）。

数值改动最贵的不是改，是三个月后没人记得为什么这么改。账本和数值源一起进版本库。

## 8. 策略系统

这是整个项目最值得打磨的部分。目标很朴素：**让一个会写 TS 的人，不读引擎源码，只看协议文档，就能把自己的打法放上战场。**

### 8.1 一套策略就是一个文件

```text
src/engine/tactics/
├── api.ts         协议：快照、意图、Tactic 接口
├── registry.ts    校验与注册：id 唯一、字段完整、来源标注
├── index.ts       注册表出口：内置 + 外部合流
├── builtin/       随仓库发布
│   ├── index.ts   内置登记表
│   ├── charge.ts
│   └── counter.ts
└── external/      外部策略包
    └── index.ts   外部登记表
```

- 内置与外部**分目录存放**、共用同一套接口与同一个注册表；界面按下拉里的分组展示。
- 加一套策略 = 放一个文件 + 在对应登记表里写一行。引擎、配置页、仿真脚本都不用动。
- 外部策略在当前版本随仓库一起静态加载（`import`），改完重开一局即生效，但需要重新构建。
- 运行时加载（拖拽文件夹、清单文件、热更新）尚未实现，见 §8.3 与 §8.7 的路线图。

### 8.2 一套策略的字段

| 字段             | 必填 | 说明                                                                 |
|:---------------- |:---- |:-------------------------------------------------------------------- |
| `id`             | 是   | 小写 slug，全局唯一；与已注册策略撞名会被跳过并在控制台报错           |
| `name`           | 是   | 展示名，允许中文                                                     |
| `author`         | 是   | 署名，用于区分策略包                                                 |
| `version`        | 是   | 策略自身版本，约战时便于区分                                         |
| `description`    | 是   | **唯一的一段自述**：打法、性格、难度、适用场景都写在这里              |
| `accent`         | 是   | 印章配色：`vermilion` / `jade` / `gold` / `ink`                       |
| `glyph`          | 否   | 印章单字，缺省取名字首字                                             |
| `createMemory`   | 是   | 每局调用一次，返回策略自己的跨 tick 记忆                              |
| `decide`         | 是   | 每 125ms 调用一次，返回 `{ 单位 id: 意图 }`                           |

元数据不再拆成「风格 / 难度 / 标签」四份：一段 `description` 承载全部说明，界面上只有这一处文案，避免四个字段各写一半、拼起来互相矛盾。

### 8.3 三层管道（路线图）

| 层   | 输入               | 输出                                 | 只做这件事                               |
|:---- |:------------------ |:------------------------------------ |:---------------------------------------- |
| 感知 | 只读快照 + 时间步  | 自己的局势视图（纯数据）             | 算距离、找威胁、判阶段；不决定行动       |
| 指挥 | 快照 + 局势视图    | 每个单位的任务（去哪、打谁、干什么） | 分配角色与目标；不关心技能能不能放       |
| 执行 | 快照 + 视图 + 任务 | 白名单意图                           | 把任务落成这一 tick 的动词；不做长期规划 |

分层不是为了好看，是为了**让不同水平的人从不同层切入**：新手只写指挥，老手才去抠执行。

> 当前版本只有 `decide` 一层：它同时承担感知、指挥与执行。下面的分层是扩展方向，引擎尚未提供默认层与按层加载。

每层只暴露一个入口函数，参数与返回值都是纯数据；引擎按清单声明的入口加载，不依赖层的内部结构。

### 8.4 只读快照

每次决策重新构建，改它不会影响战局。内容包括：

- 时间、阶段、局时、是否加时、加时预计还剩多久；
- 双方基地的位置、血量与存活状态；
- 己方全部单位，以及可见敌方单位的位置、血量、形态、技能是否就绪、脱战与复活信息；
- 己方半场的星位拓扑（象能去哪、哪些点相邻）；
- 本局生效的数值（只读，用于策略自己算阈值）。

快照里**没有引擎对象、没有函数引用、没有可变引用**。策略拿到的是一份数据，不是一把钥匙。

### 8.5 意图白名单

每个单位每个决策 tick 只能表达一条意图；技能是瞬时触发，移动与目标是持续到下一 tick 的状态。

| 意图                  | 参数    | 引擎的裁决                                                                               |
|:--------------------- |:------- |:---------------------------------------------------------------------------------------- |
| `MOVE_TO`             | 目标点  | 单位可移动（基地、象、非移动形态的炮不可）、目标点被 clamp 进棋盘；士被额外 clamp 进防区 |
| `MOVE_DIR`            | 方向    | 单位可移动、方向非零；位置仍受棋盘与防区约束                                             |
| `ATTACK_TARGET`       | 目标 id | 目标存在、存活、属于敌方                                                                 |
| `SHOOT_NEAREST`       | —       | 交给内部机制自动索敌                                                                     |
| `DEPLOY` / `UNDEPLOY` | —       | 仅炮；形态必须匹配；强制逃跑期间忽略                                                     |
| `CAST_JUMP`           | 目标 id | 仅马；冷却就绪、形态允许、距离落在起跳窗口内                                             |
| `TELEPORT_ANCHOR`     | 星位 id | 仅象；冷却就绪、目标星位与当前星位「田」字相邻、未被另一只象占用                         |
| `IDLE`                | —       | 本 tick 不主动移动；防御性自动攻击仍然生效                                               |

白名单不是安全补丁，而是设计：**策略的创造力应该花在「用有限的动词打出花」，而不是「绕过规则」。**

两条使用约定：

- `ATTACK_TARGET` 同时承担接近：目标不在攻击距离内时，单位会朝它移动；进入距离后停下开火。
- 移动意图不会关闭自动攻击：路过敌人时仍然会还手，只是移动会被交战减速。

### 8.6 意图的生效与拒绝

- 每个决策 tick 开始时清空上一轮意图；没有收到新意图的单位不主动移动。
- 技能意图（跃击、传送）是瞬时动作，触发后由单位自己的状态机接管，不会每一 tick 重复触发。
- 拒绝原因必须分类可见：未知单位、非己方单位、已阵亡、未知动作、参数缺失、目标非法、超出距离窗口、冷却中、星位不相邻、星位被占用、形态不允许。
- 控制台显示每个策略的拒绝计数与最近若干条样本；批量仿真把拒绝数计入统计。

### 8.7 加载、校验与约战

- **来源**：内置目录与 `external/` 目录在构建时静态加载；运行时导入尚未实现。
- **校验**：加载时检查 id 形状与唯一性、必填字段、`accent` 枚举、`decide` / `createMemory` 是否存在。不合规的策略被跳过并列出问题，不会静默顶替。
- **取用**：`findTactic(id)` 可能返回 `undefined`；`getTactic(id)` 找不到直接抛错并列出现有 id——不再回落到某套默认策略打完一局。
- **隔离**：策略在决策循环里同步执行，异常被捕获并计入 `errors`；尚未提供沙箱、超时与指令预算，因此外部策略必须是可信代码。
- **可观测**：控制台与战报里能看到每个策略的拒绝数、异常数与决策次数。
- **可约战**：`pnpm sim --red <id> --black <id> --matches N` 用固定种子批量对跑。
- **可迭代**：改完策略重开一局即生效，不需要重启应用。

### 8.8 内置策略是标尺，不是「最强 AI」

- **全军冲锋**：不读血量、不回防、不撤退，见谁打谁。它存在的意义是给出一个「最朴素的打法能打成什么样」的基准线。
- **防守反击**：读基地血量差、读入侵者、残血回城、加时按比分选择死守或反推。它衡量「理解规则」能换来多少胜率。

一把量新策略，一把量数值改动。内置策略越像「性格」，越不像「答案」，这个项目就越健康。

### 8.9 写第一个策略

1. 在 `builtin/` 或 `external/` 建一个文件，导出一个 `Tactic`：id、名字、作者、版本、一段完整的 `description`。
2. 在对应目录的 `index.ts` 登记一行。
3. `pnpm sim --red <你的 id> --black counter` 和内置策略约战，看拒绝原因与战报。
4. 固定种子重复跑，确认改动带来的是稳定收益，而不是一次好运。

## 9. 观战控制台

控制台只做三件事：**让人能改、能看、能复现。**

| 能力   | 内容                                                           |
|:------ |:-------------------------------------------------------------- |
| 能改   | 策略、局时、数值、预设；改完立刻生效，可回滚，可对比           |
| 能看   | 战况、双方基地、单位指标、胜率与对阵、结构化日志、被拒绝的意图 |
| 能复现 | 种子 + 配置 + 策略 = 一局；可导出、可分享、可并排比较          |

### 9.1 必须可见的信息

- **战局**：已进行时间、阶段、局时剩余、是否加时、加时预计还剩多久、双方基地血量、双方兵力。
- **单位**：选中后能看血量、形态、技能冷却、当前意图、脱战与复活状态。
- **策略**：名称、作者、加载状态、本局决策耗时、非法意图数、异常次数。
- **统计**：胜率、对阵矩阵、时长分布、逐兵种存活率 / 输出占比 / 复活次数 / 技能命中。
- **日志**：结构化事件流，可筛选、可导出；配置错误与策略拒绝必须能定位到具体字段或单位。

### 9.2 四条原则

1. **没有隐藏开关。** 任何影响结果的输入都必须在界面上可见、可改、可追溯。
2. **异常必须显性。** 配置越界、策略加载失败、决策超时、意图被拒——全部说清原因，不许静默降级。
3. **控制台不参与模拟。** 关掉界面，战局照样能跑完；它只是订阅者。
4. **信息密度优先于装饰。** 它是实验室的仪表盘，不是游戏大厅。

本文不规定它的布局、配色与组件划分——那是实现者的工作，只要满足上面四条。

## 10. 表现层

### 10.1 战场渲染

- **只读订阅。** 连续的状态用于插值，瞬时的事件用于表现；渲染从不回写引擎，引擎也从不等待动画。
- **可读性第一。** 混战中要能一眼看清：谁在哪、谁快死了、谁正在开火、哪边基地在掉血。木质与玉石质感是这个战场的气质，不是目的。
- **绘制有层次。** 地形 → 范围与防区指示 → 单位 → 弹体 → 特效 → 信息叠加（血条、意图线、星位网）。层次错了，特效就会盖住战况。
- **可整体降级。** 特效、粒子和音频可以全部关闭，画面仍然完整可读，判定分毫不差。
- **表现参数与平衡参数分开存放。** 调观感永远不该碰数值源，反之亦然。

本文不描述具体动画如何实现、观感如何调教——那属于实现与美术判断，不属于规则设计。

### 10.2 音频合成

- **零素材。** 碰撞、开火、爆炸、传送、复活、基地告破，全部由代码实时合成；没有网络请求，也没有解码等待。
- **语义驱动。** 引擎只发布「发生了什么」，音频层自己决定「听起来像什么」；音色是参数，可整体换主题。
- **混战治理。** 同一事件不能叠成噪音，要有优先级、并发预算与整体限幅；但基地告破、加时开始这类事件必须穿透出来。
- **可控。** 总开关、总音量、分组音量；页面在后台或无头运行时自动静音。

渲染与音频互不调用，只共享同一个事件源。

## 11. 项目结构

```text
.
├── src/
│   ├── engine/            纯 TS 规则内核（零 DOM / 零框架）
│   │   ├── battle.ts      固定步长、物理、状态机、胜负、统计
│   │   ├── board.ts       棋盘、阵型、九宫、星位
│   │   ├── config.ts      单一数值源 + 校验 + 匹配参数缩放
│   │   ├── simulate.ts    无头单局 / 批量
│   │   └── tactics/       策略协议、注册表、两套内置策略
│   ├── render/            Canvas 2D 战场 + Web Audio 合成
│   └── ui/                Vue 3 配置页、观战页、HUD 组件
├── tests/                 确定性、契约、黄金对局（20 条）
├── scripts/sim.ts         无头批量仿真 CLI
├── docs/
│   ├── architecture.md    实际架构、帧生命周期、确定性、差异
│   ├── tactic-api.md      策略协议与意图白名单
│   └── balance-log.md     调参账本
└── ...
```

依赖方向严格单向：`ui → engine`、`render → engine`、`sim → engine`。引擎不允许反向依赖任何应用层代码，也不允许引入运行时框架。

三条硬约束：

1. `src/engine` 的依赖树里只有 TypeScript 标准能力。
2. `src/engine` 不导出任何 UI 组件、样式、音频节点。
3. `src/ui` / `src/render` 不允许出现规则计算；它们只做展示、转发与表现。

## 12. 开发与验证

### 12.1 验证金字塔

| 层       | 验证什么                                               |
|:-------- |:------------------------------------------------------ |
| 单元测试 | 几何换算、伤害结算、状态机切换、复活与回血、意图校验   |
| 契约测试 | 第 7.5 节的设计不变量，任何一条挂了就不许合入          |
| 回归测试 | 固定种子下的「黄金对局」：结果指纹、关键指标、结束阶段 |
| 性能测试 | 大棋盘满编交战时，模拟与画面都还能保持可交互           |

### 12.2 完成标准

一个功能算「做完」，要同时满足：

- 无界面能跑完一整局，并输出完整统计；
- 同一配置、同一对策略、同一组种子，重复跑结果一致；
- 契约测试全绿；
- 关掉渲染与音频，对局结果不变；
- 配置写错时，能在界面上定位到具体字段；
- 外部策略包不改一行引擎代码就能加载、参战、被统计。

### 12.3 调参闭环

**改数值 → 跑契约 → 跑批量 → 读胜率与兵种指标 → 记一笔账本 → 再改。**

这条闭环跑得越顺，这个项目越接近它想成为的东西。

## 13. 路线图与非目标

### 13.1 路线图

> v0.1 已完成 1–5 的可用版本；第 6 项（外部策略生态）与回放分享链接留待后续。

1. **内核骨架**：配置、实体、固定步长、胜负——能无界面跑完一局并输出统计。
2. **规则完整**：兵种机制、复活与加时、意图校验、统计口径全部到位。
3. **战场渲染**：棋盘、棋子、血条、受击与技能反馈，先可读，再好看。
4. **音频合成**：语义事件到音色的映射，混战不糊。
5. **观战控制台**：热调、图表、日志、策略切换、复现。
6. **策略生态**：外部包导入与隔离、约战与对阵矩阵、示例库。

### 13.2 在此之上

- **回放**：一局 = 种子 + 配置 + 策略，天然可回放；把回放做成可分享的链接。
- **参数敏感性**：批量跑出「哪个旋钮最影响胜率」，让调参从试错变成排序。
- **策略排行榜**：固定配置下的循环赛，给社区策略一个可比较的坐标。
- **观战解说层**：把关键事件翻译成人话，让没读过规则的人也能看懂一场仗。

### 13.3 非目标

- 不做玩家操棋，不做联机匹配——这是观战与调参工具，不是竞技游戏。
- 不追求写实 3D 与素材级音效——表现服务于可读性。
- 不把引擎做成通用游戏框架——它只服务这一盘棋。
- 不为「更多特效」牺牲一帧的确定性。

## 14. 术语表

| 术语         | 含义                                                       |
|:------------ |:---------------------------------------------------------- |
| **常规军**   | 车、马、炮、兵；有底座，阵亡后读条复活                     |
| **精英**     | 士、象；阵亡后读条极长（士 45s / 象 60s），加时按倍率缩短，靠自愈回血 |
| **底座**     | 常规军出生点上的不可攻击区域，提供回血与复活；棋盘上有复活标记 |
| **星位**     | 象可以传送到的七个固定点，只有「田」字相邻的点互通         |
| **加时**     | 局时归零后的决战阶段：复活加速（含士象）、双方基地等速流血 |
| **意图**     | 策略能表达的唯一东西：移动、攻击、形态、位移技、待命       |
| **快照**     | 每次决策生成的只读战场数据，不含引擎对象与可变引用         |
| **契约**     | 用不变量守住设计意图的测试，不是「好不好玩」的证明         |
| **标尺**     | 内置策略的定位：量新策略、量数值改动，而不是「最强 AI」    |
| **黄金对局** | 固定种子与配置下，结果被记录为基准的回归测试               |

> 先把规则做对，再把战场做美。
> 数值和策略，永远比画面更值得打磨。
